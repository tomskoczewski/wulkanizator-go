# Domain Distillation — Wulkanizator GO

A map of the business domain as it exists in the source documents and in the code, and of the gaps
between the two. No production code is written here; every code claim is a path and line range that
was opened and read.

## 0. Context discovered

**Requirements documents exist**, so this distillation is not limited to README + code:

| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |

| `context/foundation/roadmap.md` (v1)                                                | What actually shipped (F-01, F-02, S-01…S-04 `done`; S-05, S-06 `parked`), the north star, the baseline                |
| `context/foundation/tech-stack.md`                                                  | Starter and stack rationale (`10x-astro-starter`, Supabase, Cloudflare Workers)                                        |
| `README.md`, `AGENTS.md`                                                            | Operational domain knowledge not in the PRD: workshop/role provisioning, trigger kill-switch, the naive-time hard rule |

| Layer       | Location                               | Domain content                                                                                                                                                    |
| ----------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UI          | `src/pages/*.astro`, `src/components/` | Status advance rules re-applied client-side (`DayPlanBoard.tsx:82-117`), booking flow (`NewAppointmentForm.tsx:63-303`)                                           |
| HTTP        | `src/pages/api/`                       | Validation + status-code mapping only (`api/appointments/index.ts:8-39`, `api/appointment-status/[id].ts:8-47`)                                                   |
| Validation  | `src/lib/schemas/`                     | Zod; carries two real domain rules (`workshop-setup.ts:47-50`, `appointment.ts:25`)                                                                               |
| Services    | `src/lib/services/`                    | Pure rules (`slot-suggestions.ts`, `day-plan.ts`, `appointment-transitions.ts`, `status-failure.ts`) + I/O orchestration (`appointments.ts`, `workshop-setup.ts`) |
| Persistence | `supabase/migrations/`                 | A substantial share of the domain: RLS scoping, the overlap exclusion constraint, `book_appointment()`, `normalize_phone()`                                       |

**There is no domain layer.** No `src/domain/`, no entity/aggregate types beyond row aliases
(`src/types.ts:18-26` re-exports generated table rows). Domain rules live in two separated places —
`src/lib/services/*.ts` and SQL — with no module that owns a rule end to end.

### #1 to refactor: the **Bay schedule** aggregate, with booking as its only entry point

Why this one:

1. **The invariant is the product.** "Two visits on the same bay at the same time is a regression
   worse than paper" (`prd.md:46`) is the strongest statement in the document, and it is also Risk
   #2 in the test plan — "a booking write accepts a slot the workshop cannot serve — a double-booked
   bay, **or a time outside working hours**" (`test-plan.md:46`). The second clause is precisely the
   half that nothing structural holds.
2. **The rule is spread across three altitudes.** `suggestSlots()` computes what is free
   (`slot-suggestions.ts:64-79`), `bookAppointment()` re-derives and re-checks the choice
   (`appointments.ts:185-195`), and the exclusion constraint catches the race
   (`…20260821090000…:56-61`). That layering is deliberate and sound for _overlap_. The asymmetry is

## Summary

This artifact maps Wulkanizator GO's domain from `prd.md`, the roadmap, the operational docs and the
code, and reports the distance between them. The Ubiquitous Language table holds 23 terms, of which
**five carry "BRAK w kodzie"** — tire storage, the customer's car, the price list, revenue/forecast,
and seasonality — all of them parked or deferred rather than forgotten, and two of them (tire storage
and revenue) load-bearing in the vision and in the access-control model respectively. Two terms run
the other way: `phone_normalized` and naive workshop-local time are real, consequential domain
decisions that exist only in code and in a lessons entry, never in the model. The subdomain split
puts slot suggestion, the appointment lifecycle and the day plan in the core, configuration and
customer identity in support, and auth/scoping in generic — with one strategic tension worth naming:
the vision calls tire storage the thing no competitor has, and the roadmap parks it. Twelve
model-vs-code drifts are listed; the ones that would surprise a reader of the PRD are that no code
path can ever cancel an appointment (D2), that the API accepts any status pair rather than the
documented path (D3), and that the worker/bay assignment the access-control section promises does
not exist (D1). **The most important conclusion is D4/D5:** the guardrail the PRD calls "worse than
paper" is only half-held at the trust boundary — `book_appointment()` enforces _who_ may book and
_whose_ bay, but takes the caller's word for _when_ and _how long_, so the overlap constraint is
airtight while "matches the service duration" and "inside opening hours" are enforced nowhere below
the application layer. That is the #1 refactor: pull the two time derivations into the aggregate's
single entry point and let the application layer's preflight go back to being a UX nicety.
